# 여러 꽃의 가림을 줄이는 배치 수정

사용자가 실제 Unity 이미지에서 꽃이 겹친다고 지적한 내용을 반영했다. 주간 식물의 메시 버전을 4에서 5로 올리고, 같은 식물의 꽃 수·성장·기억 연결을 유지하면서 꽃의 위치와 방향을 분산한다.

이 문서의 수치는 버전 5 검증 결과다. 이후 [입체감 개선과 메시 버전 6](PLANT_VOLUME_2026-11-04.md)이 적용됐으며, 현재 `FlowerLayoutTests`는 최신 메시 버전을 검사한다.

## 원인과 변경

기존 로우폴리 스타일은 꽃을 최대 2.5배 확대했지만, 원래 생성기의 꽃 배치 검사는 확대 전 템플릿을 사용했다. 캐모마일 등 단일 꽃송이의 법선도 모두 위쪽이었다. 여기에 세로 비율을 0.78로 줄여 가까운 꽃들이 화면에서 겹쳤다.

새 `PlantFlowerLayout`은 기본 Recipe 위에 결정적인 꽃 배치 단계를 적용한다.

- 실제 확대된 꽃의 완성 모습·봉오리·열매 기하로 공간을 측정한다. 최종 세로 비율도 가림 평가에 반영한다.
- 종 확정 때 고정된 최종 꽃송이 수에 맞춰 크기 예산을 먼저 잡는다. 첫 꽃이 공간을 모두 차지하지 않게 한다.
- 꽃대 위치 후보의 방위각·반경·높이를 탐색한다. 수평 거리만 벌리는 대신 높이 차이도 사용하며 꽃대는 원래 줄기 부착점과 연결한다.
- 캐모마일·코스모스·장미류는 바깥쪽으로 22~30도, 다른 형태는 8~16도 기울인다. 꽃송이의 작은 꽃 묶음은 종의 형태를 유지하며 간격을 넓힌다.
- 3차원 여유 공간과 8개 방향의 투영 겹침 점수를 함께 비교한다. 한 카메라를 따라 꽃이 회전하는 방식은 아니다.
- 각 꽃은 자신의 시드·저장된 형질·앞선 꽃의 배치만 사용한다. 뒤에 꽃이 추가돼도 이미 있는 꽃의 위치·기울기·크기가 바뀌지 않는다. 줄기가 자라는 동안에는 기존 성장점을 따라 움직인다.
- 최대 64개 배치 결과를 메모리에 보관한다. 키에는 기하 입력만 포함하며 감정 본문을 넣지 않는다. 외부에는 복사본을 반환한다. 저장 자료를 다시 읽거나 캐시가 비워져도 같은 결과를 계산한다.

새 꽃 배치는 카메라 방향 전체에서 가림이 작아지는 후보를 선택한다. 모든 각도에서 모든 꽃이 완전히 보이는 것을 보장하지 않으며, 자연스럽게 묶여 피는 작은 꽃들까지 완전히 분리하지 않는다.

## 저장 자료 처리

새 주간 식물은 메시 버전 5를 사용한다. 이미 만든 주간 식물 중 버전 4인 식물도 다음 앱 상태 로드에서 5로 이관한다. 완성한 주간 식물도 대상이다. 이관은 레이아웃 검증 후 하나의 저장으로 처리하며 실패하면 기존 파일을 유지한다.

성장 단계·꽃 수·시드·영양제·활동 기록·기억 잎 ID·원본 기록은 바꾸지 않는다. 이전 영양제 구매 방식의 보관 식물과 메시 버전 1~3은 그대로 유지한다. 버전 4의 렌더러도 남아 있어 같은 Recipe를 사용한 전후 비교가 가능하다.

## 검증 방법

`tests/FlowerLayoutTests.cs`는 12종을 고정 시드로 생성하고 모든 1~21단계의 공간 경계·삼각형 예산을 검사한다. 성장 시 기존 꽃 배치 유지, 저장 복원, 캐시 복사본 격리, 실제 꽃 수 보존, 저장 실패 시 이관 취소를 확인한다. 기록이 있는 저장 자료에서는 메시 버전 외의 XML이 동일한지도 비교한다.

가림 측정은 같은 Recipe의 버전 4와 5를 각각 방위각 8개, 고도 27도에서 CPU로 투영한다. 각 꽃송이를 혼자 그렸을 때의 픽셀 중 다른 꽃송이의 깊이에 가려진 비율을 구하고 꽃송이·뷰·식물별로 평균한다. 한 꽃송이 안의 작은 꽃은 한 묶음으로 처리한다. 잎·줄기·그림자는 제외한 **꽃끼리의 가림** 측정이며 사람의 미적 선호나 터치 사용성 결과는 아니다.

Unity 6000.3.24f1에서는 같은 시드·조명·카메라로 대표 3종의 전후 비교와 4방향 비교, 12종과 기억 잎 21개, 9개 성장 단계를 렌더링했다. 실제 정원에서도 잎 선택→기록→복귀, 회전·확대 보존, 보관 식물의 기록에서 해당 식물로 복귀를 확인했다. 비교 이미지의 왼쪽은 버전 4, 오른쪽은 버전 5다.

최종 실행은 12종 × 100시드 = **1,200개 식물**, 8방향의 **9,600개 전후 쌍**이다. 22,807개 검증을 통과했고, 꽃송이의 평균 가림 비율은 **17.28% → 0.65%**로 감소했다. 완성 식물의 기본 메시 최대값은 4,356삼각형이었다. 모든 25,200개 성장 갱신에서 공간 경계·메시 예산 검사를 통과했다. 시드·종 입력은 합성이며 사람의 실제 활동 분포를 뜻하지 않는다.

Windows X64 / .NET 10.0.12의 이번 CPU 파일럿에서 캐시가 있는 메시 생성은 중앙값 1.84 ms, 95백분위 3.15 ms였다. 캐시를 지운 뒤 최초 꽃 배치 계산만 측정하면 각각 25.36 ms, 50.38 ms다. 후자는 최초 표시·새 꽃 구조·캐시 만료 때 추가될 수 있는 비용이며, Android 프레임 성능을 증명하지 않는다.

기존 생성기 56,253개와 종 미리보기 15개, 주간 식물 644개, Focus 활동 1,676개, 외형 이관 115개 검증도 통과했다. 렌더링 비교와 실제 정원 연결은 Unity에서 별도로 통과했다.

## 재실행

```text
python3 scripts/test-weekly-plants.py FlowerLayoutTests
python3 scripts/test-weekly-plants.py WeeklyPlantTests FocusMissionStateTests GardenPlantAppearanceTests
python3 scripts/test-procedural-plants.py
```

`CAPSTONE_FLOWER_SEEDS`는 종당 시드 수이며 기본값은 12다. `CAPSTONE_FLOWER_OUTPUT`을 무시된 `artifacts/` 하위 경로로 지정하면 `occlusion.csv`와 `report.txt`를 저장한다. Unity는 그래픽을 켜고 `CapstoneDesign.EditorTools.WeeklyPlantValidation.FlowerSpacing`을 실행하며, 출력 위치는 `CAPSTONE_ARTIFACTS`로 지정한다. 공통 QA 목록에는 `flower-layout`과 `flower-spacing`을 추가했다.

이번 로컬 원본과 실제 렌더링은 `artifacts/flower-spacing-20261104/`에 보관한다. 모두 합성 자료이며 저장소에 이미지·CSV·로그를 게시하지 않는다. Android 실기기의 생성 지연·프레임 시간과 손가락 선택 정확도는 별도 검증이 필요하다. 배치 후보 탐색 비용은 새 꽃 구조를 처음 계산할 때 발생하므로, 캐시 사용 시 메시 시간과 최초 배치 시간을 구분해서 측정한다.
