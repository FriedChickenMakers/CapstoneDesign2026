# 공학적 가치 확대 후보 — 2026-10-27

이 문서는 후속 개발을 선택하기 위한 **제안**이다. 아래 기능을 이번 UI 폭 수정 작업의 추가 완료 조건으로 삼거나, 모두 구현하기로 확정한 것은 아니다. 논문·공식 문서의 방법을 현재 프로젝트에 적용하는 방안이며 프로젝트의 실제 사용자 효과를 입증한 결과도 아니다.

**2·4주가 주력일 수 있다.** 8주 이력이 쌓인다고 가정하지 않으며, 2주 12회·4주 24회 코스에서 확보할 개인별 관측은 제한적이다. 활동 횟수와 알림 결정 횟수도 서로 같지 않다. 표본 부족 시 기본 정책을 유지하고, 실제 관측량을 확인한 뒤 학습 범위를 넓힌다.

## 현재 기반과 우선순위

이미 구현된 기반은 기간별 코스·진도, 로컬 추천과 알림 시각 조정, 선택적 행동 이벤트 큐·인증·멱등 API·삭제, 로지스틱 정책 평가/추론, 건강 데이터 출처·결측 표시, 절차적 식물 생성, 자동 검증 실행기다. 운영 서버 배포, 모든 알림 이벤트 생산자의 연결, 실제 참여자 대상 개선 효과는 별도다. 근거는 [구현 검증](QA_IMPLEMENTATION_VALIDATION_2026-10-27.md), [서버 계약](../server/README.md), [건강 조회](HEALTH_CONNECT_FINDINGS.md), [식물 평가 계획](PLANT_GENERATION_EVALUATION_PLAN.md)을 따른다.

우선 추천은 다음 세 가지다.

1. **식물 비교 실행기:** 기존 평가 계획을 실제 재현 가능한 결과로 연결해 프로젝트 고유의 생성 기술을 설명한다.
2. **알림 관측·무작위 비교 기반:** 서버와 모델이 필요한 이유를 실제 전달·행동 변화의 비교로 설명한다. 온라인 학습은 이후 단계다.
3. **수집 신뢰도 처리:** 워치·휴대폰 수집 공백과 동기화 지연이 잘못된 개인화 입력으로 이어지는 것을 줄인다.

## 1. 알림 효과를 학습하는 개인화

- **현재 → 추가:** 클릭 시각 군집 기반 조정과 활동 응답 모델에, 알림의 예약·게시·차단·클릭·활동 시작 기록 및 무발송 대조를 연결한다. 이후 contextual bandit으로 어떤 상황에서 보낼지 학습한다.
- **작은 MVP:** 사용자 허용 시간 내 후보 시점과 무발송을 비교한다. 정책 버전·결정 당시 특징·선택 확률·전달 상태를 저장하고, 기존 알림 상한·완료 억제·거부 설정을 유지한다. 단순 규칙 대 무작위 비교부터 시작한다.
- **지표:** 결정 후 사전 지정한 시간 안의 활동 시작/완료율, 반응시간 분포, 알림 수 대비 완료, 거부·중단율. 클릭률만 최적화하지 않는다.
- **선결조건·평가:** 전달 실패와 무반응을 구분한다. Android 게시 성공은 사람이 듣거나 봤다는 증거가 아니다. 실제 참여자 비교는 동의와 연구 절차를 갖춘 뒤 수행하고, 동일인의 반복 관측과 시간 경과를 분석에 반영한다. 짧은 코스에서 개인별 학습이 충분하다고 가정하지 않는다.
- **난도:** 관측·제한적 비교는 중, 안정적인 온라인 학습 및 실사용 평가까지는 상.
- **1차 출처:** [Personalized HeartSteps](https://arxiv.org/abs/1909.03539)는 맥락에 따라 제안 여부를 학습하는 사례다. [MRT 설계·분석 논문](https://pmc.ncbi.nlm.nih.gov/articles/PMC9276848/)은 반복 결정 시점의 무작위 비교 설계를 다룬다. 이 연구의 운동 결과를 우리 마음챙김 앱의 효과로 전용하지 않는다.

## 2. 수집 신뢰도를 반영하는 개인화

- **현재 → 추가:** 출처, 측정 시각, 결측 구간, STALE/PARTIAL 상태를 추천 입력의 품질 근거로 묶는다. 이미 있는 표시를 넘어 입력 사용·보류를 일관되게 결정한다.
- **작은 MVP:** 권한·조회 완결 여부·최신성·수집 구간·출처를 별도 값으로 유지하고, 근거가 부족하면 기본 추천으로 복귀한다. 임의 가중치의 단일 “건강 신뢰 점수”부터 만들지 않는다.
- **지표:** 관측 가능한 구간의 충족률, 동기화 지연 분포, 결측을 0으로 오판한 비율, 불완전 입력을 사용한 추천 비율, 기본 정책 복귀 비율.
- **선결조건·평가:** 데이터 종류별 기대 수집 간격이 알려진 경우에만 충족률의 분모를 정의한다. 권한 철회·지연·부분 조회·출처 중복을 주입한 합성 사례와 실제 기술 상태를 확인한 표본으로 검증한다. Health Connect의 BPM만으로 원시 PPG 품질·HRV 정확도를 판정하지 않으며, 직접 관측하지 못한 워치 충전 여부를 추정하지 않는다.
- **난도:** 중. 현재 메타데이터로 시작 가능하며 별도 생체 판정 모델은 필요하지 않다.
- **1차 출처:** [RADAR-base 공식 구조](https://radar-base.org/docs/concepts-and-components-of-radar-base/)의 데이터 검증·시간 구간 집계·품질 모니터링을 참고한다. 그 시스템 전체나 대규모 스트리밍 인프라 도입이 전제는 아니다.

## 3. 유효성과 다양성을 함께 확보하는 식물 생성

- **현재 → 추가:** 종별 생성기·검증기와 문서화된 distance 평가를 실제 비교 실행기로 만든다. 필요하면 MAP-Elites로 유효한 개체를 높이·폭·기관 밀도 등의 형질 공간에 분산하는 탐색을 추가한다.
- **작은 MVP:** 공통 3형태 × 100시드로 현 생성기와 매개변수·확률적 L-system 구현을 비교한다. 이후 탐색을 추가할 경우 같은 후보 평가 예산에서 무작위 탐색과 MAP-Elites를 비교한다.
- **지표:** 생성 실패·형태 위반율, 유효 개체 간 특징/실루엣 거리, 중복률, 사전 고정한 형질 공간의 점유율, 생성 지연. 자연스러움·선호는 방법을 가린 짝 비교로 따로 측정한다.
- **선결조건·평가:** 같은 종·성장 단계·표본 수·렌더링 조건을 사용한다. 거리 정규화 범위와 형태 제약을 실험 전에 고정하고 실패도 분모에 포함한다. 거리 증가만으로 품질 우위를 주장하지 않는다. L-system도 절차적 생성이므로 비교 대상은 구체적인 두 구현이다. 상세 설계는 [기존 평가 계획](PLANT_GENERATION_EVALUATION_PLAN.md)을 따른다.
- **난도:** 비교 실행기는 중, 제약과 탐색을 포함한 생성기 개선은 중~상.
- **1차 출처:** [PCG Benchmark](https://arxiv.org/abs/2503.21474)는 품질·다양성·제어 가능성을 분리한다. [MAP-Elites 원 논문](https://arxiv.org/abs/1504.04909)은 선택한 형질 공간의 다양한 해를 보존한다. 식물 비교 구현은 [L-Py 원 논문](https://www.frontiersin.org/journals/plant-science/articles/10.3389/fpls.2012.00076/full)을 참고한다.

## 4. 재시작·오프라인에서 복구되는 증분 동기화

- **현재 → 추가:** 현재 영속 이벤트 큐·멱등 API와 Unity 실행 중 전송에 네이티브 지속 작업을 연결한다. Health Connect 조회에는 타입별 변경 체크포인트와 수정·삭제 반영을 별도로 추가한다.
- **작은 MVP:** 행동 이벤트 한 종류를 WorkManager로 전송하고 재시작·재전송·철회 경합을 검증한다. 건강 데이터 증분 캐시는 별도 로컬 경로로 만들며 현재 행동 이벤트 API에 원본 건강 기록을 추가하지 않는다.
- **지표:** 유실·중복률, 재접속 후 복구 시간, 동기화 지연, 전송량, 삭제 후 재유입 여부.
- **선결조건·평가:** 전송 담당과 저장소 소유권을 하나로 정해 Unity와 Worker의 중복 처리를 막는다. Health Connect는 타입별 권한·백그라운드 읽기 지원을 확인하고, 토큰 만료 시 재조회·중복 제거 경로를 갖춘다. ACK 유실·프로세스 종료·네트워크 단절·오래된 업로드를 주입한다. 정시 실행을 보장한다고 표현하지 않는다.
- **난도:** 중~상. 새로운 큐 자체보다 수명주기와 삭제·재시도 일관성이 핵심이다.
- **1차 출처:** [Android offline-first 공식 문서](https://developer.android.com/topic/architecture/data-layer/offline-first)는 영속 큐·WorkManager·재시도를, [Health Connect 동기화](https://developer.android.com/health-and-fitness/health-connect/sync-data)는 변경 토큰·삭제·만료 복구를 다룬다.

## 5. 기기 안에서 학습하는 소형 개인화 모델

- **현재 → 추가:** 서버에서 평가한 로지스틱 정책의 기기 내 추론에 개인별 계수·보정값의 로컬 갱신을 추가한다. 원본 행동 이력은 이 학습을 위해 전송하지 않는다.
- **작은 MVP:** 현재 네 특징을 쓰는 소형 온라인 로지스틱 모델을 C#으로 비교한다. 최소 관측량·두 결과 클래스·모델 만료/되돌리기 조건을 정하고 표본이 부족하면 기본 정책을 유지한다. 더 큰 모델의 필요성이 확인될 때 LiteRT를 검토한다.
- **지표:** 미래 구간의 Brier score·log loss·보정 오차, 추론/학습 지연, 메모리, 기본 정책 복귀 비율.
- **선결조건·평가:** 학습 당시 특징을 고정하고 아직 닫히지 않았거나 동기화가 불완전한 결과 창은 음성 사례로 확정하지 않는다. 같은 사용자 미래 구간과 미관측 사용자 평가를 구분하며, 예측 정확도 개선을 추천 정책의 인과 효과로 해석하지 않는다. 2·4주 데이터만으로 충분히 개인화된다는 전제도 두지 않는다.
- **난도:** 중. 실제 우위 입증은 관측량에 좌우된다. 네 특징만을 위해 대형 런타임·LLM·연합학습을 먼저 도입하지 않는다.
- **1차 출처:** [LiteRT on-device training 공식 문서](https://developers.google.com/edge/litert/conversion/tensorflow/build/ondevice_training)는 기기 데이터를 외부로 보내지 않고 모델을 갱신하는 방법을 제공한다. C# 소형 모델 MVP는 프로젝트 규모에 맞춘 적용 제안이다.

## 6. 행동 순서를 생성하는 상태 기반 자동 테스트

- **현재 → 추가:** 정해진 단위·통합·기기 시나리오에 코스 전환·완료·저장 실패·재시작·철회를 조합하는 자동 탐색을 추가한다.
- **작은 MVP:** 서버의 동의/전송/철회 상태부터 Hypothesis stateful로 검사한다. 이후 명령 실행 어댑터로 실제 C# 진도·보상 도메인을 호출하고 실패 순서를 최소 재현 사례로 축소한다.
- **지표:** 상태 전이·경계 조합 커버리지, 의도적으로 심은 결함의 검출률, 최소 재현 순서 길이, 재실행 재현율. 테스트 수만으로 전체 기능 검증을 주장하지 않는다.
- **선결조건·평가:** 구현을 그대로 복사하지 않은 작은 명세 모델과 실제 제품 코드를 비교한다. 합성 저장·가상 시각을 쓰고 seed와 실패 입력을 보존한다. 보상 중복·일일 한도·철회 후 업로드 같은 불변 조건을 사전 정의한다.
- **난도:** 중. 기존 자동화에 독립적으로 추가할 수 있다.
- **1차 출처:** [Hypothesis stateful 공식 문서](https://hypothesis.readthedocs.io/en/latest/stateful.html)는 원시 동작을 조합해 실패 순서를 찾고 간단한 모델과 비교하는 방식을 설명한다.

## 7. 기기 성능·발열에 맞추는 정원 렌더링

- **현재 → 추가:** 정원·안개·bloom에 프레임 시간과 지원되는 열 상태를 이용한 품질 조절을 추가한다.
- **작은 MVP:** 글자와 UI 해상도를 유지하면서 3D 렌더 스케일·안개·그림자 비용의 두 단계 품질을 비교한다. 상하 임계값과 유지 시간을 달리해 품질이 반복 전환되는 것을 막는다.
- **지표:** p95/p99 프레임 시간, 긴 프레임 비율, 품질 전환 빈도, 열 상태, 동일 조건의 전력 소모. 지원되지 않는 측정은 추정값으로 채우지 않는다.
- **선결조건·평가:** A7과 휴대폰의 API 지원을 각각 확인하고, 열 상태를 읽을 수 없는 기기는 프레임 시간 기반으로 동작한다. 같은 장면·밝기·충전 상태·실행 시간으로 고정 품질과 비교하고 시각 품질 저하도 함께 검토한다.
- **난도:** 중. 효과 판단에는 장시간 실기기 측정이 필요하다.
- **1차 출처:** [Android ADPF 공식 문서](https://developer.android.com/games/optimize/adpf)는 기기의 동적 열·성능 상태에 맞춘 작업량 조절을 다룬다. 해당 기능 전부가 모든 프로젝트 기기에서 지원된다는 뜻은 아니다.

## 선택 후 남길 공통 결과

선택한 후보마다 baseline, 사전 지정 지표·허용 조건, 데이터/정책 버전, 재현 절차, 실패와 미측정 범위를 남긴다. 합성 검증, 실기기 기술 검증, 실제 사용자 비교를 구분한다. 공학적 지표가 개선되어도 우울 증상이나 치료 효과가 입증된 것으로 서술하지 않는다.
