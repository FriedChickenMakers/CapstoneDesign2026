# Local state and cycle rules

Status: IMPLEMENTED / UNIT_TESTED with synthetic fixtures on bundled Unity Mono. Android filesystem replacement and IL2CPP runtime serialization require device validation; these unit results do not establish device durability.

`Assets/Scripts/Runtime/LocalGardenState.cs` is a Unity-independent domain. `GardenStateService` is the only gameplay writer; Kotlin health readers do not access this store. The UI must call `Open` successfully before rendering playable state, handle `false` and `LastError`, and dispose the service at shutdown. All mutations clone the committed state, save the complete candidate, and publish only on success. `Snapshot` is detached. Completed session, receipt, nutrient, course IDs and course position commit together. Preview is read-only; purchase debit, placement/growth and request receipt commit together.

The file uses schema 1 XML with SHA-256 checksum, a flushed temporary file and atomic replace, retaining the previous file as `.bak`. A lifetime `.lock` prevents simultaneous writers. The checksum detects accidental corruption, not malicious tampering. XML DTOs are retained by `LocalState/link.xml` for IL2CPP. Files must remain in app-private persistent storage. There is no cloud synchronization or cryptographic cheating prevention.

Loading also checks required XML fields, schema, typed IDs, unique record identities, non-null collections, course consistency, cycle ordering, timestamps and numeric bounds. Disposed stores cannot write after releasing their writer lock. A corrupt primary, missing primary with a backup, or interrupted first write with a temporary file fails closed. The app must show the storage error and leave play disabled. It must never automatically load an older backup and resume rewarding: that could regrant rewards committed after that backup. Recovery is deliberately manual and backup files remain intact. Power-loss durability depends on the Android filesystem; directory metadata fsync is not implemented. An orphaned temporary write can be replaced by a subsequent successful write when a valid primary exists.

Daily cycles, four-week course progress, and permanent garden state are separate fields. The cycle key is the local calendar date after subtracting `ResetHourLocal`. An injected `IClock` provides UTC and the timezone. A lexicographic date high-water mark advances only to a later cycle. A ten-day absence creates one current cycle, never ten catch-up rolls or rewards. Clock rollback and westward timezone travel retain the latest cycle until local time passes it. Eastward travel can advance to a later local date once; returning west cannot reclaim previous cycles. This is a conservative local policy, not a complete anti-cheat system. The timezone and application UTC are retained for each decision. Changing reset-hour policy after release requires an explicit migration decision.

A cycle records a visitor ID or the empty no-visitor result. Candidates must be supplied from validated content/environment rules; only `animal:` IDs are accepted. Installation seed plus cycle determines the roll; same inputs produce the same result after a failed save. Sorting candidate IDs makes list order irrelevant. A failed decision is retained in memory until a successful retry of that cycle, even if candidates change. Across a process restart, deterministic retry assumes the same content/configuration inputs; no uncommitted visitor is displayed. The configuration is copied when the service is created. Existing decisions never reroll after refresh, content updates, purchases or restart. Environment purchases affect the next cycle. Discoveries persist after departure, with no undiscovered placeholders. Visitor stay duration is currently the cycle lifetime.

Activities are selected, started, paused/resumed, ended without completion, or explicitly completed with reward committed. Selection and start timestamps are separate. A timer does not complete an activity. Completion and reward form one transaction, so there is no persisted intermediate completed-but-unpaid state. Optional mood/note may be null; no sensor or permission requirement exists. Each session has its original cycle as `InstanceId`; crossing midnight never automatically finishes it. Completion after midnight applies to that original instance. Repeating the same session is a no-op; different sessions for the same typed mission in the same cycle produce one reward receipt. The same session ID cannot be submitted twice through different entry screens; reuse for a different mission/order is rejected. Only one active activity is allowed, including concurrent selection calls. Repeated end-participation callbacks retain the original end time. If the clock rolls backward during participation, start/end bounds are clamped to avoid a negative health lookup interval; this does not attest to true elapsed time. Course progress only advances when the submitted order equals the current order, with stable completed IDs retained; it never advances with time. The catalog/UI supplies validated mission/order pairs; the domain bounds order to 1–28, rejects future selections and changed order for an already-known mission, but does not embed product content.

Internal IDs use `course:`, `free-mission:`, `plant:`, `environment:`, and `animal:` prefixes. Display names are never save keys. Environment slots are trimmed and case-normalized, cannot overlap, and the same environment cannot be purchased twice. Purchase request IDs share one namespace across growth/environment, preventing one request from charging twice through different entry points. Reuse with a different target or action is rejected using persisted command identities. Receipts from an earlier development save without command identities remain preserved but cannot be replayed automatically.

Migration copies existing nutrient, XP, growth, last unlock, unlock IDs and completion IDs in the first atomic write, sets `MigrationCompleted` and schema 1, and leaves PlayerPrefs untouched. Legacy completions live in `LegacyCompletedUnknownDate`, without fabricated dates or rewards. XP is never converted to nutrient. Legacy mission IDs must be distinctly prefixed (for example `free-mission:legacy-w1-body-scan`); they do not imply original Notion course completion. Submitting the same legacy typed mission never regrants its old reward. Retrying a failed migration starts from unchanged legacy values; restarting after a successful migration ignores legacy inputs.

Development defaults (`DemoBalanceConfig`, copied at construction): local reset 04:00, completion nutrient 10, environment cost 10, growth cost 10 and increment 0.1, visitor chance 50%. Daily reward limit is one per typed mission per cycle. No starter grant, automatic growth, streak reward or penalty exists. Interrupted participation gives no reward pending product policy. All of these are demonstration values, not approved team balance. No daily aggregate cap or reflection incentive has been invented.

The integration separates LIVE/MOCK/REPLAY directories; only LIVE imports legacy prefs. No mood or note contents are logged by the domain. Sessions are retained locally; retention limits and user-facing deletion remain follow-up work. Backups contain the same private data and need the same retention policy.

Run `scripts/test-local-state.sh`. It compiles the real domain with bundled Mono and tests transactions, repeated sessions/restarts, migration and failure, clock/timezone changes, daily boundaries, no catchup, stopped participation, course ordering, immutable snapshots/previews, overlap, purchase/growth idempotency, visitors/discoveries, file reload, exclusive writer, checksum corruption, preserved backup, interrupted first-write detection, actual staging-path I/O failure/retry, semantic XML corruption, concurrent selection/completion, disposed writers and command identity conflicts.

## Runtime integration

`WeekOneQuestDemo` retains its original scene component identity but routes all
new gameplay writes through `GardenStateService`. The original PlayerPrefs
remain untouched. Known legacy quest IDs are imported as
`free-mission:legacy-<old-id>` with unknown completion date; none is relabelled
as Notion P01. LIVE reads legacy preferences; MOCK/REPLAY start separate saves
under `garden-mock` / `garden-replay` and never import LIVE preferences.

`MockupNavigation` is always active and checks the cycle every 30 seconds and
on focus return even while the activity panel is inactive. Opening a new
session first requires successful cycle persistence. Leaving a preview through
bottom navigation cancels its temporary geometry/scale without spending.
Draft reflection text survives a failed completion save within the current app
process; an unsubmitted draft is not persisted across process death.
