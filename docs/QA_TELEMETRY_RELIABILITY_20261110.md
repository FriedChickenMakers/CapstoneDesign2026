# 2026-11-10 QA 수집·전송 안정성 점검

이 문서의 실기기 결과는 서면 동의 후 운영자가 수동 등록한 APK의 측정 전송 검사다. 이후 추가하는 자동 등록은 [자동 등록·로그 수집 운영 문서](AUTOMATIC_TELEMETRY_ENROLLMENT.md)에 분리해 기록한다. 자동 등록은 후속 단위·Unity·외부 서버 검증과 별도 A7 debug probe의 실제 오프라인 수신을 확인했다. 이 결과를 과거 수동 등록 검사나 표준 non-debuggable 최종 APK의 실기기 검사와 섞지 않는다. 앱 내 동의 화면, 건강 원본 수집, 미션·보상 정책은 추가하지 않는다. 아래 검사용 APK의 장애·오프라인 전송 검사와 최종 **1007 APK**의 복귀·방문 검사를 구분하며, 전체 배포 판정은 [최종 QA 기록](QA_RELEASE_20261110.md)을 따른다.

## 요구사항 대조와 수집 범위

확인한 자료는 Docs 저장소의 `QA·베타 측정 구현 범위와 발표 근거`, `Google Docs b·c·h 진행표와 세부 설계 2026-11-06`, 코드 저장소의 `QA_BETA_MEASUREMENT_PLAN.md`와 Google 원문의 **1104회의록**이다. Google 원문은 2026-11-04 수정본으로, UI 조작 횟수·미션 수행까지 걸린 시간 및 QA 평가 지표를 제안한다. 이 제안을 임상 효과를 입증하는 실험 설계나 건강 원본 전송 승인으로 확대하지 않는다.

`app_session_started`는 기존 schema_version=1의 허용 사건 종류를 확장한다. 외부 서버에 해당 종류 지원을 먼저 배포했고 최종 1007의 수신을 확인했다. 기존 알림/활동 payload는 변경하지 않는다. 이벤트는 `live`/`synthetic`을 구분하며, 앱 방문 측정도 치료 효과가 아니다. 이번 운영자 QA 자료는 `live` 실행 경로라도 참여자 평가·D7/D14·알림 최적화 효과 분석에서 제외한다.

## 익명 식별과 인증

앱은 Android ID·광고 ID·IMEI·기기 serial을 전송하지 않는다. 과거 수동 배포에서는 운영자가 설치/참여 단위의 난수 subject와 token을 발급했다. 추가 구현하는 자동 등록 APK는 첫 LIVE 실행에 설치별 256-bit 난수 token을 private 저장소에 만들고, 서버가 token 해시를 난수 subject에 연결한다. 기존 수동 등록은 덮어쓰지 않으며 같은 등록은 앱 재시작·인플레이스 업데이트에도 유지된다. 앱 삭제·데이터 삭제 후 새 설치에는 다른 ID가 생성된다. 서면 명부와 연결한다면 엄밀히는 **가명 자료**이며, 이름과 무관한 난수라는 이유만으로 완전 익명 자료라고 단정하지 않는다.

과거 1008·1010 APK에는 공유 등록 키가 없었다. 자동 등록 빌드에는 private 외부 설정에서 가져온 공유 등록 키를 넣고, 이 키는 신규 등록과 최초 등록 전 철회에 사용한다. 실제 측정 업로드는 HTTPS와 서로 다른 설치별 bearer token으로 인증한다. APK 공유 키는 추출 가능하므로 최소 등록 장치이며 강한 기기 인증을 주장하지 않는다. RSA 개인키는 넣지 않는다. 철회·재등록 차단과 최초 등록 전 삭제 경계는 후속 외부 HTTPS 검증에서 확인했다. 작업 입력/로그에 실제 키·token을 복제하지 않으며 Android 백업 제외 정책을 유지한다.

## 전송 변경

- 방문 정의를 Android `ActivityLifecycleCallbacks`의 실제 START/STOP과 `SystemClock.elapsedRealtime`에 맞추어 native 방문 키를 공급한다. C#의 기존 등록·수집 허용 검사는 유지하며, 키보드/시간 선택의 focus·pause만으로 방문을 늘리지 않는다. 이 변경을 Unity pause callback 버그의 확인·해결이라고 설명하지 않는다. A7의 HOT 복귀 후 방문이 없었던 사례를 더 조사한 결과, 복귀 직후 native SIGSEGV와 프로세스 종료가 확인됐다. crash stack은 `vulkan.bengal.so`의 Vulkan 명령 경로와 `libunity.so`를 가리키며, 같은 기기에서는 이전 빌드에서도 유사한 드라이버 충돌 기록이 있었다. 당시 뒤이어 관측한 새 방문은 HOT 복귀 성공이 아니라 새 프로세스의 시작이었다. 이후 해당 A7 조합에 한정한 GLES 대체 경로를 적용한 최종 1007에서 같은 프로세스의 복귀·새 방문을 확인했다. 방문 lifecycle 변경만으로 Vulkan 충돌을 해결한 것은 아니다.
- 기존 Unity 전경 동기화에 **native WorkManager** 경로를 추가했다. 새 관측 뒤 5초 지연의 고유 작업과 15분 주기의 고유 작업을 등록한다. `KEEP` 정책으로 새 사건 때문에 이전 재시도 backoff가 계속 초기화되지 않는다.
- 연결된 네트워크가 조건이며 1분 시작 exponential backoff를 사용한다. 부팅 후 WorkManager가 저장된 작업을 복원한다. 전경 복귀 때도 기존 Unity 동기화 대기 시간을 초기화한다.
- 과거 전송 검사의 native 요청은 HTTPS 원점의 `/measurements/batch`이며 redirect를 따라가지 않는다. 자동 등록 추가 경로는 최초 401일 때 같은 원점의 `/enrollments`를 호출한 뒤 같은 batch를 재시도한다. 연결 10초/읽기 15초 제한, 응답 64KiB 제한, 실행당 최대 4×100 사건으로 네트워크·메모리 사용을 제한한다.
- 실패·timeout·비정상 ACK는 큐를 지우지 않는다. ACK는 보낸 ID의 부분집합만 인정하고, 일부 ACK 후에는 나머지를 재시도한다. native/Unity 중복 전송은 서버 사건 ID 중복 제거와 원자 ACK로 처리한다.
- 등록 변경·삭제·reset epoch·MOCK 전환을 확인하여 오래된 작업이 새로운 수집 구간을 지우지 못하게 한다. 저장 성공 후 네트워크를 수행하므로 앱 종료가 기록의 유일한 저장 경로가 되지 않는다.
- 빈 heartbeat는 업로드 경계를 전달하되 로컬 상태 변화가 없으면 outbox 파일을 다시 쓰지 않는다. 중복 ACK도 동일하다.
- 네이티브 측정 큐는 1,024 pending/8,192 receipts, 최대 90일이다. 가득 차면 새 사건을 거절하고 거절 횟수를 표시한다. 무한 저장을 보장하지 않으며 운영 중 누락 지표를 점검해야 한다.
- 기존 C# 추천 특징 `/events/batch` 큐는 전경 재시도 소유권을 유지한다. 새로운 native 작업은 해당 XML을 다른 writer로 수정하지 않는다. 알림·전체 미션·Focus 추천·앱 방문은 native 측정 경로에서 백그라운드 전송 가능하다.

Android Doze/절전 정책은 네트워크와 작업 실행을 지연할 수 있다. 이번 구현은 제한을 우회하지 않고 기록을 보존해 유지보수 구간/전경 복귀/네트워크 복구 후 재시도한다. 사용자가 앱을 강제 중지하거나 제조사 제한으로 작업이 차단되면 앱 재실행 전까지 전송 지연이 가능하다. 앱 삭제·데이터 삭제·영구 저장 장치 고장은 복구 가능한 오프라인 전송과 별개다. [Android WorkManager 작업·재시도](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work), [Doze·App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby).

### 실기기에서 확인한 범위

- `offline-mission07`은 USB 연결에서 Wi-Fi를 끄고 실제 활동을 시작해 대기 사건 1건을 만든 검사다. Doze와 절전 중에도 큐에 동일 사건이 유지됐고, 연결·전원 상태를 원복한 뒤 WorkManager가 앱 전경 재진입 없이 재시도했다. 서버 대조 결과는 `offline07-later-delivery-private.json`의 1/1건 일치·payload 불일치 0·중복 ID 0이다. 모든 원본과 식별값은 ignored artifacts에만 보관한다.
- 즉시 전송을 보장한 결과가 아니다. 이번 검사에서는 재시도 뒤 약 1분 후 서버 도착을 확인했다. Doze 유지보수 구간·네트워크 연결·backoff에 따라 지연이 달라지므로, 복구 직후 한 번 조회해 아직 없다는 사실만으로 영구 유실로 분류하지 않는다.
- 앞선 HOT 복귀만으로 사건을 만들려던 검사들은 대기 사건이 0건이었으므로 오프라인 전송 성공으로 집계하지 않는다. 이후 crash buffer에서 드라이버 충돌을 확인했으며, 별도로 실제 미션 사건을 생성해 위 전송 검사를 수행했다.
- 별도 `cold-outage` 검사는 전용 API만 45초 중단했다가 복구했다. `cold-outage-later-delivery-private.json`에서 원래 사건 1/1건·전체 payload·collection 일치와 중복 0건을 확인했다. 복구 직후 아직 도착하지 않은 조회도 보존하며, 나중 자연 백그라운드 재시도 결과와 구분한다.
- 최종 1007의 `final-resume-evidence.json`은 GLES 사용과 동일 PID 복귀, 35초 HOME 두 차례·화면 잠금 뒤 새 방문을 기록한다. 최초 짧은 HOME 기준 화면에는 검사 도구의 알림창이 있었으므로 짧은 복귀 중복 없음은 마지막 `final-short-repeat`의 방문 4건 유지로 판정했다. 이전 APK의 오프라인/장애 결과를 최종 APK에서 전부 반복했다고 쓰지 않는다.
- 알림은 실제 주기 작업의 도래·게시 수락을 확인했지만, 이후 강제 중지로 알림이 제거되어 이번 실제 tap은 검증하지 못했다. 이 결과는 과거 버전의 클릭 검사와 구분한다. `cmd jobscheduler run -f`의 `Running job [FORCED]`는 Worker 실행이나 게시 증거가 아니다. 이른 강제 요청은 WorkManager 자체 주기 시각 때문에 실행되지 않았고, 이후 자연 실행에서 게시됐다.
- 위 검사는 전체 기기·장시간 서버 장애·모든 OEM 절전 정책·강제 중지·호스트/기기 재부팅을 포괄하지 않는다. 충전 케이블 연결 중 `dumpsys battery unplug`으로 절전을 시험한 부분은 **BatteryService 시뮬레이션**이며 물리적으로 배터리만 사용한 시험이라고 표시하지 않는다. 운영자 QA 자료는 참가자 효과 분석에서 제외하며, 알림 시각·학습·게시 guard의 검사 전 상태 복원과 전체 단말 설정 복원 결과는 최종 QA 기록을 따른다.

근거 파일은 ignored `artifacts/qa-release-20261110/final-resume-evidence.json`, 같은 폴더의 `final-resume-qa02/`·`final-short-repeat/`·`offline-mission07/`, `artifacts/qa-server-20261110/offline07-later-delivery-private.json`·`cold-outage-later-delivery-private.json` 및 해당 서버 snapshot이다. 실제 ID·token·원본 payload·장치 로그는 문서나 Git에 복제하지 않는다.

이 A7 실기기 검사 단계의 최종 배포는 코스 미선택 문구만 보완한 1008이다. 알림·큐·그래픽·미션 로직은 1007과 같으며, 1008 설치 뒤 같은 등록의 서버 방문 1→2와 HOME 35초 동일 프로세스 복귀를 추가 확인했다. `final-v8-evidence.json`과 `final-device-audit-v8/result.json`에 기록했다. 전체 오프라인/Doze 검사를 1008에서 다시 수행했다고 해석하지 않는다. 단말 설정 원복은 1008 종료 후 모두 검증했고 강제 중지를 풀어 둔 상태다.

독립 Opus 리뷰에서 현재 방문이 용량 거절될 때 3초마다 같은 거절 횟수를 증가시키는 P2를 발견했다. native 실패 이유와 C# 방문별 terminal 표식을 추가하여 고쳤으며, 일시 저장 실패는 같은 키로 재시도한다. 처음 추가한 용량 테스트는 전체 큐 1,024개와 batch 100개를 혼동한 테스트 단언만 실패했다. 영속 파일의 전체 큐를 검사하도록 바로잡고 당시 최종 43개 검사가 통과했다. 당시 Android 방문 lifecycle 보강까지 포함한 native 검사는 46개였다. 아래 후속 자동 등록 검사는 58개로 구분한다. 실패 로그도 보존했다.

검증 원본은 ignored `artifacts/qa-client-reliability-1110/`에 보존한다. 서버 장애/기기 절전 해제 후의 실제 도착 시각·행 수, 재설치 등록, 화면/성능은 최종 배포 QA 기록에서 함께 대조한다. 참가자 모집·서면 절차·그룹 배정·수집 기간과 별도 export 보관 운영은 코드가 대신 결정하지 않는다.

## 후속 자동 등록 검증

새 자동 등록은 저장 helper 55·개인화 336 assertions, 실제 Unity 자동 등록 22 checks, 기존 UnityWebRequest 수동 등록 회귀 client 42·server 2 checks, native 58/58, 서버 89/89를 통과했다. 실제 외부 HTTPS 프로토콜 31 checks와 배포 후 상태 17 checks도 통과했다. 실제 A7의 별도 debug probe 1011에서는 오프라인 첫 실행의 초기 알림 설정을 마친 뒤 방문 사건 1건을 저장하고, HOME으로 나온 후 네트워크를 복원했다. 앱을 다시 열지 않고 같은 payload 1/1건이 수신됐으며 중복·불일치 0건이다.

첫 시도는 초기 알림 팝업 미응답으로 방문 사건이 없어 실패로 보존했다. 성공한 재시도와 합치지 않는다. 검사 뒤 probe subject 철회·재등록 거부, 로컬 ACK, 임시 앱 제거와 기존 A7 APK 보존·설정 원복을 확인했다. 이 검사는 표준 non-debuggable QA 1011의 설치·실행 검사가 아니다. 표준 1011 빌드·정적 preflight는 별도로 통과했으며 실제 기기 설치는 하지 않았다. 최종 화면 설정 감사에서도 미복원 항목 0건을 확인했다. 세부 근거와 공유 키·키 변경 제한은 [자동 등록 운영 문서](AUTOMATIC_TELEMETRY_ENROLLMENT.md)를 따른다.
