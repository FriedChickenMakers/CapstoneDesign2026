# 활동 추천 알림의 시간 개인화 평가

다섯 합성 페르소나에서 기존 정책과 개선 정책을 비교했다. 야간 근무자·학생·식당 운영자는 알림부터 클릭까지의 대기 시간이 감소했고, 원래 바로 반응하던 사용자는 비슷한 지연을 유지했다. 종일 휴대폰을 사용하는 경우에는 의미 없는 시간 이동을 멈췄다. 아래 수치는 **합성 사용자의 반응 모델을 이용한 정책 평가**이며 실제 이용자의 클릭률, 치료 효과, Android의 정시 전달률을 입증하는 결과가 아니다.

구현은 [ActivityReminderPolicy.kt](../Assets/Plugins/Android/CapstonePlatform.androidlib/src/main/kotlin/com/capstonedesign2026/platform/ActivityReminderPolicy.kt), 재현 가능한 평가 환경은 [NotificationPersonaEvaluation.kt](../tests/native/NotificationPersonaEvaluation.kt)에 있다. 제품의 권한·완료 억제·중복 방지와 걷기 알림은 [활동 알림 문서](ACTIVITY_NOTIFICATIONS.md)에서 별도로 다룬다.

## 비교 조건과 가상 시간

초기 추천 시각은 모두 20:00이다. 기존 정책은 변경 전인 2026-10-15의 동작을 평가 코드 안에 독립 복제했다. 08:00–21:00 제한, 같은 날짜의 6시간 이내 클릭만 학습, 클릭 시각 방향으로 25%씩 최대 15분 이동, 유효 클릭 3회 이후 적용을 그대로 유지한다. 새 코드가 바뀌어도 비교 기준까지 함께 바뀌지 않는다.

각 정책·페르소나에 대해 알림 제공 60회로 학습한 뒤, **학습을 멈춘 상태로 별도의 90일**을 평가한다. 60회에는 무응답도 포함되므로 모두 학습 관측으로 저장되는 것은 아니다. 학습과 평가의 가상 날짜 및 난수 seed를 분리했다. 학습 seed는 `801771`, 평가 seed는 `902993`이다. 학습은 2027년의 가상 날짜, 평가는 2028-03-01부터의 가상 날짜를 사용한다. 평가 기간에는 학습 상태를 갱신하지 않으므로 같은 데이터에 맞춘 뒤 그 데이터로 성능을 보고하지 않는다.

실제 시계는 변경하지 않는다. 정책 함수에 합성 timestamp를 전달하고 다음 사건 시각으로 이동하므로 현실의 수십 일을 기다리지 않는다. 이 JVM 평가는 사건을 즉시 진행하는 방식이다. `1분 = 2시간`처럼 실시간 비율을 둘 수도 있지만, 정책 계산에는 기다림이 필요하지 않다. 실제 알림 표시·클릭 경로를 확인하는 Android 검사는 아래 실기기 검증과 구분한다.

알림 시각과 무관하게 정해 둔 클릭 timestamp를 재생하지 않는다. 날짜별 사용 가능 시간대와 반응 지연을 먼저 만들고, **알림이 생긴 이후의 첫 사용 가능 시간대에서** 클릭을 생성한다. 이미 지나간 시간으로 클릭을 소급하거나 음수 지연을 0으로 바꾸지 않는다. 학습 중에는 한 번에 하나의 알림을 추적하고, 다음 발송은 클릭 이후의 다음 미래 예약 시각과 날짜를 사용한다. 이는 시각 학습을 분리하기 위한 이상적인 전달 모델이다.

## 합성 페르소나

사용 가능 시간대의 시작과 끝을 매일 같은 크기로 이동한다. 아래 `±` 범위에서 정수 분 단위의 균등 난수를 적용하며, 식당 운영자의 두 시간대는 각각 변동한다. 가능한 시간대 안에서 일반 페르소나는 추가로 1–8분, 종일 사용자는 0–3분 뒤 클릭한다. 클릭이 시간대 끝을 넘으면 다음 가능한 시간대로 이동한다.

| 페르소나 | 기본 사용 가능 시간대 | 날짜별 이동 | 첫 알림 → 첫 클릭 delta |
| --- | --- | --- | ---: |
| 야간 근무자 | 01:10–02:40 | ±35분 | 342분 |
| 학생 | 수업 후 휴식 17:20–18:10 | ±15분 | 1,298분 |
| 식당 운영자 | 14:30–16:00 및 22:00–22:45 | 각각 ±20분 | 117분 |
| 직장인 | 20:20–21:30 | ±10분 | 24분 |
| 종일 휴대폰 사용자 | 하루 전체 | 없음 | 0분 |

첫 학습 알림은 반응을 생성한다. 이후에는 각 날짜에 독립적으로 10%의 확률로 알림에 반응하지 않는 상황을 추가한다. 평가 기간의 무응답 여부는 같은 페르소나·날짜에 대해 두 정책에서 동일하다. 무응답을 늦은 클릭이나 특정 시간대에 대한 거부로 변환해 학습하지 않는다.

학생의 첫 클릭은 다음 날 발생한다. 기존 정책은 날짜가 달라 학습하지 못하며, 야간 근무자의 자정을 넘는 클릭도 같은 문제를 겪는다. 개선 정책은 발송 뒤 24시간 이내의 실제 알림 클릭을 허용해 이러한 관측을 반영한다.

## 고정 시각보다 반응 편차를 기준으로 판단

개선 정책은 최근 28개 관측에서 10분보다 늦은 반응을 정보성 표본으로 삼는다. 원형의 24시간 시각에서 밀집된 군집을 찾으므로 자정 전후를 평균해 정오로 보내거나, 서로 다른 두 휴식 시간을 무조건 평균해 바쁜 시간으로 보내지 않는다. 표본이 부족하거나 한 군집의 지지가 부족하면 시각을 유지한다.

선택한 군집의 Q20–Q80 범위를 반응 편차의 보조 지표로 사용한다. 최근 3회 반응의 중앙값이 `max(10분, min(군집 편차, 90분))` 이하면 추가 이동을 멈춘다. 그보다 늦으면 군집 앞부분을 향해 한 관측당 최대 120분 이동한다. 따라서 결과가 특정 한 분으로 영구 고정되거나 delta가 0이 되어야 성공하는 것은 아니다. 관측이 달라지면 다시 적응할 수 있다.

바로 클릭한 표본만으로는 사용자가 그 시각을 선호하는지, 어느 때든 바로 반응하는지 구분할 수 없다. 종일 사용자에게는 이러한 표본을 근거로 예약을 계속 늦추지 않는다. 이번 비교에서 기존 정책의 최대 이동은 11분, 개선 정책은 0분이었다.

**추정 범위의 한계:** 위 Q20–Q80은 `delta > 10분`인 선택된 클릭 표본의 군집 범위다. 사용자의 전체 사용 가능 시간, 수면 시간, 모집단 신뢰구간을 뜻하지 않는다. 이미 빠르게 반응하는 표본이 제외되므로 실제 하루 일정의 변동보다 훨씬 좁아질 수 있다. 예를 들어 이번 야간 근무자의 최종 군집 범위는 01:45–01:46이지만, 합성 사용 가능 시간대 자체는 ±35분 변동한다. 이 군집 범위를 “사용자가 이 1분에만 반응한다”거나 “전체 변동을 1분 정확도로 추정했다”고 해석하면 안 된다. 성능 판단은 아래 별도 평가 기간의 delta 분포를 우선한다.

## 사전에 정한 평가 기준

개선 정책의 결과를 보기 전에 다음 기준을 평가 코드에 고정했다. 실행 결과에 맞춰 통과 기준을 조정하지 않았다.

- 각 페르소나의 p90 delta는 `2 × 날짜별 이동 폭 + 최대 반응 지연 + 15분` 이하여야 한다. 실제 일정의 변동과 반응 시간을 허용하며, 추가 15분은 현재 주기 작업의 한 주기를 고려한 공학적 허용치다. 이번 순수 시뮬레이션이 WorkManager의 실제 지연까지 재현한다는 뜻은 아니다.
- 중앙값과 p90은 각각 기존 정책보다 15분 넘게 악화되면 안 된다. 이미 반응 지연이 낮은 경우에는 억지로 추가 개선을 요구하지 않는다.
- 기존 정책이 시간대를 찾지 못하는 야간 근무자·학생·식당 운영자는 중앙값이 적어도 70% 감소해야 한다.
- 종일 사용자의 최대 시각 이동은 5분 이하여야 한다.
- 같은 날짜의 외생 무응답 수가 두 정책에서 같아야 하며, 음수 delta와 같은 가상 날짜의 중복 발송 기록이 없어야 한다. 마지막 검사는 시뮬레이션 기록의 유효성 검사이며 제품의 중복 방지를 증명하는 검사가 아니다.

사용 가능 시간대 안에 발송된 비율도 함께 보고한다. 이 비율은 클릭을 받은 알림만 골라 계산하지 않고 평가 기간의 전체 발송 90건을 분모로 삼는다. 시간대 바로 전에 도착해도 짧은 지연으로 클릭될 수 있으므로 이 비율 하나만으로 우열을 결정하지 않는다.

## 별도 평가 기간 결과

단위는 분이다. `기존 → 개선` 순서이며, delta 통계는 실제 반응이 생성된 관측에 대해서만 계산한다. IQR은 Q75−Q25로, 반응 편차의 가운데 50% 폭이다. p90과 IQR은 정렬된 표본 사이를 선형 보간했다.

| 페르소나 | 중앙값 | p90 | IQR | 사용 가능 시간대 발송 비율 | 개선 정책의 평가 시각 |
| --- | ---: | ---: | ---: | ---: | --- |
| 야간 근무자 | 315.5 → 6 | 343.1 → 11.1 | 35.25 → 2 | 0% → 83.3% | 01:32 |
| 학생 | 1,286.5 → 6 | 1,298 → 8 | 13.25 → 4 | 0% → 97.8% | 17:34 |
| 식당 운영자 | 66 → 7 | 83 → 17 | 21 → 7 | 0% → 64.4% | 22:05 |
| 직장인 | 4 → 4 | 6 → 7 | 2 → 3 | 100% → 83.3% | 20:27 |
| 종일 휴대폰 사용자 | 1 → 1 | 2 → 2 | 1 → 1 | 100% → 100% | 20:00 |

사전에 정한 기준은 다섯 페르소나 모두 통과했다. 야간 근무자·학생·식당 운영자의 중앙값은 각각 약 98.1%, 99.5%, 89.4% 감소했다. 직장인은 중앙값이 같고 p90은 1분 늘었다. 모든 사용자에서 모든 지표가 개선되었다고 해석하지 않는다. 표의 시각은 이 학습 실행에서 선택한 평가 시각이며, 다른 seed나 사용 패턴에서도 같아야 하는 정답 시각이 아니다.

| 페르소나 | 각 정책의 평가 반응 수 | 각 정책의 무응답 수 / 전체 |
| --- | ---: | ---: |
| 야간 근무자 | 84 | 6 / 90 |
| 학생 | 84 | 6 / 90 |
| 식당 운영자 | 85 | 5 / 90 |
| 직장인 | 79 | 11 / 90 |
| 종일 휴대폰 사용자 | 79 | 11 / 90 |

무응답 수는 모델에서 외생적으로 만든 값이며 개인화가 클릭률을 개선했다는 결과가 아니다. 응답자만의 지연 통계와 무응답 수를 함께 제시해, 응답을 잃는 대신 지연이 개선된 것처럼 보이지 않게 한다. 모든 정책·페르소나의 합성 기록에서 음수 delta와 같은 날짜 중복 발송 수는 0이었다.

## 재현

저장소 루트에서 실행한다. Kotlin compiler 및 JDK는 기존 네이티브 정책 검사와 같은 설치 경로를 기본으로 사용하며 `KOTLIN_GRADLE_LIB`, `JAVA_BIN`으로 바꿀 수 있다.

```sh
scripts/test-notification-policy.sh
scripts/test-notification-personas.sh
```

기존 정책 결과만 따로 남기려면 다음처럼 실행한다.

```sh
NOTIFICATION_PERSONA_OUTPUT=artifacts/notification-personas/baseline \
  scripts/test-notification-personas.sh --baseline-only
NOTIFICATION_PERSONA_OUTPUT=artifacts/notification-personas/comparison \
  scripts/test-notification-personas.sh
```

평가 출력은 지정한 디렉터리의 `summary.json`, `trials.csv`, `results.txt`다. `summary.json`에는 기준, seed, 지표, 위반 목록이 들어 있다. `trials.csv`에는 합성 발송·클릭 시각과 학습 중 시각 변화가 들어 있다. 출력 디렉터리는 무시되는 `artifacts/` 아래에 두며 실제 사용자 기록과 혼합하지 않는다. 조건 위반 시 실행은 실패로 종료한다.

Android 검사는 [build-notification-test-apk.sh](../scripts/build-notification-test-apk.sh)와 [NotificationValidationInstrumentation.kt](../tests/android/notifications/NotificationValidationInstrumentation.kt)를 사용한다. 기기 연결·설치·복구는 별도의 실기기 절차다. 문서나 예제에는 실제 기기 식별자·무선 ADB 주소·사용자 건강 기록을 포함하지 않는다.

## 해석 범위와 다음 검증

이 평가는 날짜별 사용 가능 시간대가 지정한 분포를 따른다는 가정과 고정된 학습·평가 seed를 사용한다. 다양한 독립 seed, 근무 교대·시험 기간처럼 패턴이 바뀌는 경우, 며칠간 미사용, 알림 피로에 따른 무응답, 해외 이동 등의 일반화 성능을 입증하지 않는다. 실제 사용자 연구를 대체하지 않는다.

식당 운영자에게는 두 시간대가 있지만 20:00 이후 첫 반응은 주로 야간 휴식에서 관측된다. 이 결과는 관측 가능한 야간 시간대로 적응했음을 보여준다. 사용하지 않은 오후 시간대까지 모두 발견하거나 두 시간대의 상대 선호도를 학습했다는 뜻은 아니다.

전달 모델은 알림이 선택한 시각에 생성된다고 가정한다. 실제 Android에서는 권한, 채널 차단, Doze, 앱 강제 중지, 주기 작업 지연, 소리·진동 억제가 별개의 변수다. 실제 화면에 알림이 표시되는지, 클릭 PendingIntent가 제품 경로로 들어오는지, 예약 회차·완료·중복 처리가 일치하는지까지 실기기에서 확인해야 한다. 표시 성공과 소리·진동 발생도 구분한다.

## A7 실기기 검증

제품과 분리한 합성 테스트 패키지를 A7에서 실행했다. 다섯 페르소나 각각 40회, 총 **200회의 실제 `NotificationManager` 게시와 실제 `PendingIntent` 자동 실행**을 수행했다. 클릭 시각은 가상 시간이고 터치 입력을 사람이 수행한 검사는 아니다. 학습 표본이 제품과 같은 알림 진입 경로를 통해 저장되고 재초기화 뒤에도 유지되는지 확인했다. 기기의 실제 OS 시각은 변경하지 않았다.

전체 실행은 실제 시간 52.951초였으며 465개 검사 조건을 통과했다. 같은 조건을 매 게시·클릭 때 반복 확인한 횟수가 포함되므로 **465개의 독립 시나리오**를 의미하지 않는다. 별도의 오류·전달 검사에는 다음이 포함된다.

- 예약 전에는 생성하지 않고, 가상의 예정 시각에는 Android의 실제 표시 알림 목록에 도달하는지 확인했다. 같은 예약 회차의 재시도는 중복 게시하지 않으며, 다음 회차는 이전 표시 알림을 갱신할 수 있다.
- 직접 호출과 함께 실제 WorkManager 작업자도 실행해 알림 생성 및 작업 성공 상태를 확인했다. 이 검사는 장시간 Doze 이후의 정각 전달 보장이 아니다.
- 알림 게시 예외, 게시 전 저장 실패, 게시 후 확인 저장 실패를 주입했다. 실패 후 재시도와 저장된 미확정 게시 내역의 복구가 가능하며, 이미 보이는 알림은 다시 소리 효과를 요청하지 않고 확인 처리하는지 검사했다.
- 자정 이후 지연 도착을 이전 예약 회차로 기록하고 다음 회차를 막지 않는지, 새벽 예약을 실제로 게시할 수 있는지 확인했다. 완료·알림 끄기·MOCK 상태의 억제도 검사했다.
- 26분 늦게 게시하고 그로부터 10분 뒤 클릭하는 합성 사례에서 학습 delta가 36분이 아닌 10분인지 확인했다. 예약부터 게시까지의 시스템 지연과 게시부터 클릭까지의 사용자 반응을 구분한다.
- 동일 클릭의 재학습 방지, 명시적인 시간 변경 시 학습 초기화, 변경 전 알림의 늦은 클릭이 초기화를 되돌리지 않는지 검사했다. 설정을 반복 조회하거나 알림 기능을 재초기화하는 것만으로 시간이 이동하지 않는지도 확인했다.

모두 같은 페르소나별 p90 허용 기준을 만족했다. 위 JVM 비교와 실기기 결과의 시각이 다른 것은 동일한 학습 시퀀스를 다시 실행한 비교가 아니기 때문이다. A7는 2032년의 가상 날짜에서 40회 모두 반응을 생성해 학습했고, 2033-04-01부터의 별도 90일을 평가했다. JVM 비교는 2027년의 60회 알림과 일부 무응답으로 학습하고 2028년에 평가했다. 날짜마다 난수 환경이 달라지므로 최종 한 시각의 일치보다 평가 기간 반응 분포가 허용 범위에 있는지를 확인한다.

**표시와 소리의 구분:** 최초 테스트 채널은 중요도 3(`DEFAULT`)이고 소리가 설정되어 있었지만, 시스템의 interruption filter는 2(`PRIORITY`, 방해 금지의 우선순위 모드)였다. 검사는 실제 표시 생성과 클릭·작업자 경로를 검증했으며 스피커 소리를 청취하거나 마이크로 측정한 검사는 아니다. 200회 페르소나 검사는 소음을 방지하려고 별도 테스트 패키지의 채널 중요도를 낮춰 수행했다. 제품 채널, 시스템 소리 설정과 사용자의 알림 권한을 강제로 바꾸지 않았다.

이 실행의 근거는 무시되는 출력 디렉터리의 `android-results.json`, `android-virtual-trace.json`, `android-channel.json`에 보관한다. 공개 문서에는 합성 결과만 정리한다.

### 제품 빌드와 마무리 검증

같은 변경 사항으로 Unity Android 제품 APK를 빌드하고 서명을 검증한 뒤 A7에 데이터 유지 방식으로 업데이트했다. 설치된 APK의 SHA-256이 빌드 결과와 일치했고, 최초 실행 전 기존 설정·정원 저장 파일의 바이트 일치와 기존 센서 행의 보존을 확인했다. 제품 UI에서 설정의 24시간 선택창을 열어 새벽 01:00 선택이 가능함을 화면과 UI 계층으로 확인했다. 선택은 취소했으며, 사용자의 기존 알림 시간·활성화·자동 조정·입력 모드 설정이 유지된 것을 다시 확인했다.

2026-10-16 최종 확인에서 제품 프로세스가 실행 중이고 해당 프로세스의 보관된 logcat에 조사 대상 런타임 예외가 없었다. 별도 합성 테스트 패키지는 제거했고, 임시로 변경한 화면 꺼짐 시간·밝기·밝기 모드를 원래 값으로 복원한 뒤 다시 읽어 일치 여부를 검증했다. 원시 로그, 설정, 화면 캡처, 백업 및 복원 기록은 공개 저장소에 포함하지 않는다.
